# Specification for attempts

This is the problem statement given to models that write attempts. It is self-contained,
and deliberately leaves out any discussion of methods, related work or difficulty.
`premise.md` is the fuller document for people.

## 1. Setting

- There are `N` threads, `M` blocks (numbered `0..M-1`) and `K` sync points (numbered
  `0..K-1`).
- An **action** is a `Read` of one block, or a `Write` of one block with some data.
  - Every action has a **start** and an **end**.
  - A thread may start several actions before any of them ends, so one thread's actions
    may overlap in time.
- A thread's program is a sequence of **steps**. A step is one of:
  - the start of an action;
  - the end of an action (the end comes after the start, in the same thread);
  - an **event** on a sync point (§2).
- Each thread's steps are totally ordered: this is its **program order**.

## 2. Sync points

Each sync point `h` is a virtual step `ĥ` that belongs to no thread. An event on `h` is
one of:

| Event | Meaning |
|---|---|
| `before(h)` | this step comes before `ĥ` |
| `after(h)` | this step comes after `ĥ` |
| `at(h)` | this step is the same instant as `ĥ`; it is identified with `ĥ` |

In particular, all `at(h)` steps of all threads are one single instant. A sync point that
no event mentions is still a virtual step, unrelated to every other step.

## 3. Trace poset and linearizations

- The **trace poset `P`** has the following elements:
  - every start and end;
  - every `before`/`after` event;
  - every virtual step `ĥ` (each `at(h)` step is identified with `ĥ`).

  Its order is the transitive closure of three relations: program order (with `at(h)`
  replaced by `ĥ`), `x < ĥ` for every `before(h)` step `x`, and `ĥ < x` for every
  `after(h)` step `x`. Well-formed setups make `P` acyclic.
- A **linearization** `L` is a total order of all elements of `P` that extends its order.
  The position of an element in `L` is its timestamp. **`Lin(P)`** is the set of all
  linearizations.
- Under `L`, every action `a` has an **interval**
  `I_L(a) = [pos(start(a)), pos(end(a))]`.

## 4. Data and block semantics

- **Terms.** Block contents are terms, built from these leaves:
  - constants (natural numbers);
  - `init.b`: the unknown initial content of block `b`;
  - `w`: the unknown content of write `w`, when its data is `"*"`.

  Terms are combined with pairs `a~b`. Terms are compared **structurally**: two terms are
  equal only if they are identical trees. In particular `a~b ≠ b~a`, a pair never equals a
  leaf, and an unknown symbol equals only itself.
- **Initial content.** Each block's initial content is a constant, or `init.b`.
- **Write data.** An expression over:
  - constants;
  - `"*"` (the whole data: unknown, the write's content is the symbol named by its id);
  - references to earlier reads of the same thread whose **end** precedes the write's
    start in program order (standing for the value that read returned);
  - references to earlier writes of the same thread whose start precedes it (standing
    for that write's content);
  - pairs of these.

  A write's content is its expression with each reference replaced by its value.
- **Effect points.** A **full schedule** is `(L, π)`: a linearization `L`, plus an effect
  point `π(a)` for every action. `π(a)` is a real number in `I_L(a)`, and different
  actions have different effect points.
- **Atomic block semantics.** Process the actions in increasing order of `π`, with every
  block starting at its initial content:
  - a write sets its block's content to its own content;
  - a read returns its block's current content.

  The **final content** of a block is its content after all actions.

## 5. Observations, feasibility and possibility sets

- Some reads carry an **observed** result (a term).
- A full schedule is **feasible** if every observed read returns exactly its observed
  term.
- `L` is **feasible** if there is some `π` for which `(L, π)` is feasible.
  **`LinFeas(P)`** is the set of feasible linearizations. Without observations,
  `LinFeas(P) = Lin(P)`.
- **`Poss(r)`** is the set of terms read `r` returns over all feasible full schedules.
  **`Poss(b)`** is the set of final contents of block `b` over all feasible full
  schedules.
- **`Poss_L(r)`** and **`Poss_L(b)`** are the same, with `L` fixed.
- The setup is **consistent** if at least one feasible full schedule exists.
- "Exactly" means no more and no less: every listed term must be produced by some
  feasible full schedule, and every term some feasible full schedule produces must be
  listed.

## 6. Cases

| Case | Sync points | Observed reads |
|---|---|---|
| `b` | none (`K = 0`) | none |
| `s` | allowed | none |
| `o` | none (`K = 0`) | allowed |
| `so` | allowed | allowed |

A setup in a case may also be one of the simpler cases, e.g. a case-`so` setup may have
no sync points or no observations. There are no other kinds of action.

## 7. Tasks

- **linear.** Enumerate `LinFeas(P)`: every feasible linearization, each exactly once,
  and nothing else. Optionally, count it: give `|LinFeas(P)|`, and `|Lin(P)|` if
  available.
- **solver.** Compute exactly `Poss(r)` for every read `r` and `Poss(b)` for every block
  `b`, together with whether the setup is consistent. Over all linearizations is
  required; for one given `L` is optional.

Correctness is graded first, on many setups, including adversarial ones. Speed is graded
second: each call has a time limit, and larger setups are timed.
